# DB-Deadlock-Agent 目标草图

> **用法**：学习过程中产生的想法、启发、设计灵感随时往里加。比如学 MCP 时想到"用 MCP 暴露锁状态"、学 RAG 时想到"用向量库存 schema 文档"。开始写代码时回头翻一遍，不会漏掉好想法。

## 一句话

**用自然语言驱动多个 AI Agent 并发操作数据库，Agent 自动检测并解决死锁。**

## 为什么做这个

- rookieDB 的 LockManager 已有完整的多粒度锁实现，但**完全没有死锁检测**——两个事务互相等待时无限期阻塞
- 传统死锁检测是写死在数据库内核里的（超时 or wait-for graph），但我想试试让 **AI Agent 来做这件事**
- 本质上是在验证一个想法：**能不能把数据库内核的一部分逻辑（死锁检测）外包给 AI？**

## 最终形态

```
用户（自然语言）
    │
    ▼
┌───────────────────────────────────────┐
│  Orchestrator Agent                   │
│  "同时执行这两个查询"                   │
└───┬───────────────┬───────────────────┘
    │               │
    ▼               ▼
┌──────────┐  ┌──────────┐
│ Agent A  │  │ Agent B  │    ← 各自独立操作 rookieDB
│ 查学生表  │  │ 更新课程  │
└────┬─────┘  └────┬─────┘
     │             │
     └──────┬──────┘
            ▼
┌───────────────────────┐
│ rookieDB              │
│  LockManager          │
│  ├─ T1 持有 S(Students)，等 X(Courses)
│  └─ T2 持有 X(Courses)，等 S(Students)
│       ↑ 死锁！          │
└───────────────────────┘
            │
            ▼
┌───────────────────────┐
│ Deadlock Detector     │  ← 定期查询锁状态
│ 构建 wait-for graph   │
│ 检测环 → 选 victim     │
│ 通知 Agent 或 kill 事务 │
└───────────────────────┘
```

## 核心技术问题

1. **锁状态怎么暴露给 Agent？**
   - rookieDB 的 LockManager 内部有锁表和等待队列，但对外接口有限
   - 需要给 LockManager 加接口（如 `getWaitForGraph()`），通过 socket 或新端点暴露

2. **死锁怎么检测？**
   - 构建 wait-for graph：节点 = 事务，边 = T_a 等 T_b 释放锁
   - BFS/DFS 找环 → 有环 = 死锁

3. **检测到死锁后怎么办？**
   - Victim selection：选最年轻的事务 kill，或选持有锁最少的事务
   - 通知用户哪个事务被回滚了，为什么

4. **Agent 怎么"理解"死锁？**
   - 不是写死的 if-else，而是把锁状态用自然语言描述给 Agent
   - Agent 分析后决定策略，甚至能解释死锁成因

## 核心认知

**这个项目的价值不在于"实现了一个死锁检测算法"——BFS 找环谁都会写。**

**价值在于**：把传统数据库内核的职责（死锁检测）交给 AI Agent，让 Agent 通过自然语言理解锁状态、做出决策、向用户解释。

这是一个**AI + 数据库内核**的交叉实验。成了就是一个很有意思的 demo：传统 DB 逻辑可以被 AI 替代或增强到什么程度？
